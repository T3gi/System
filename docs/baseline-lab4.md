# Базова лінія продуктивності Super Loop (Baseline)

Документ фіксує найгірші показники швидкодії та використання пам'яті прошивки з архітектурою super loop (ЛР3), отримані в сценаріях S1–S4 (штатна робота, передача кадру, обрив і коротке замикання I2C) і в другій серії `docs/metrics/run_*.log` (20 натискань кнопки з потоком команд UART, відновлення I2C, перезапуск; зведення — `docs/metrics/summary.txt`), див. `docs/fault_tolerance_report.md`. Ці дані — еталон для порівняння після переходу на FreeRTOS у ЛР4. У ЛР4 ті самі сценарії треба повторити тим самим способом вимірювання.

## 1. Показники швидкодії

| Метрика | Найгірше зафіксоване значення | Сценарій | Причина у Super Loop | Очікування після FreeRTOS |
| :--- | :--- | :--- | :--- | :--- |
| **Найдовше блокування циклу** | **30 875 мс** за SysTick (≈31,5 с реально, бо SysTick стоїть під час читання камери) | S2 | Блокувальна передача кадру CIF (9 смуг × 22 528 Б у base64) по UART 115200 | Інші задачі виконуються під час передачі; передача через DMA |
| **Джитер `TICK` (max)** | **+31 306 мс** під навантаженням; **+12 мс** штатно (у 24 % періодів), **+34 мс** макс. за годину при зміні стану заслінки | run_btn, S2; S1, S3, run_long_1h | Немає витіснення; мітка періоду ставиться за фактом запуску; зсув від `camera_task` | ≤ 1 мс (`vTaskDelayUntil`) в обох випадках |
| **Затримка реакції на кнопку** | звичайна робота: 0–3 мкс типово, **61,1 мс** макс. (n = 10); під час передачі кадру: **7,5…19,5 с**, медіана 17,6 с (n = 10); S2: 107,2 мс; оцінка найгіршого проходу без команд ≈ 513 мс | run_btn, S2 | Прапорець з EXTI обробляється лише тоді, коли цикл дійде до `Process_Button_Event()` (очікування кадру, рядки камери, `TICK`, стирання сектора) | Мікросекунди до запуску задачі обробки (витіснення) |
| **Вартість збою I2C** | +23 мс на перше невдале читання, далі 0 | S4 | Таймаут/помилка всередині `HAL_I2C_Mem_Read` | Без впливу на інші задачі |
| **Відновлення після збою I2C** | не відбувається: ≥ 24 с після повернення SDA без жодного вдалого читання; відновлює лише Reset | S3, S4, run_i2c_recovery, run_reset | Немає процедури відновлення шини | Окрема задача-наглядач з відновленням шини, ≤ 2 с |
| **Команди UART під час довгої операції** | 20 / 20 прийнято, `ore = 0`, `drop = 0`; відповіді — лише після кінця передачі (до ≈ 31 с) | run_btn | Консоль опитується в тому ж циклі | Відповідь ≤ 100 мс |
| **Час від Reset до `READY`** | ≈ 5,2–5,3 с (з них ≈ 3 с огляд серво, 1,2 с автоекспозиція камери) | run_i2c_recovery, run_reset | Послідовна самоперевірка | + ініціалізація ядра і створення задач |
| **Відставання системного часу** | ≈ 2,4 % (5 хв блокування ≈ 5,1 хв) | S1 | `__disable_irq()` на ≈16 мс на кожен кадр камери | Без змін, доки камера читається з вимкненими перериваннями; потрібне DMA |
| **Втрати UART RX** | 0 (`ore = 0`, `drop = 0`) | S1–S4, run_* | Прийом через переривання в кільцевий буфер 256 Б | 0 |
| **LOAD** | 87–99 % | S1–S4 | Метрика рахує частку часу в `App_Poll()`; процесор насправді зайнятий опитуванням 100 % часу | Заміряти частку часу Idle Task — реальне завантаження |

**Тривала робота (run_long_1h, 1 год):** 3 596 запусків `TICK`, 0 пропусків, +11–12 мс у 24 % періодів, макс. +34 мс; 0 помилок температури і втрат UART; LOAD і частка порушень сталі протягом години.

**Не виміряно в ЛР3:** точка зламу, зникнення живлення під час запису, час стирання сектора W25Q64 на стенді. Вибірка натискань — 10 + 10 замість 30–50.

## 2. Використання пам'яті

| Метрика | Значення (Super Loop) | Джерело | Очікування від FreeRTOS |
| :--- | :--- | :--- | :--- |
| **Кількість стеків** | 1 (MSP): і цикл, і переривання | архітектура | Окремий стек на кожну задачу (PSP) + MSP для переривань |
| **Зарезервований стек** | 1024 Б (`_Min_Stack_Size = 0x400`) | `STM32F411xx_FLASH.ld` | Сума стеків задач + стек переривань |
| **Пік використання стека** | не виміряно | `stack_paint()` викликається на старті, але `stack_report()` ніде не викликається | `uxTaskGetStackHighWaterMark()` для кожної задачі |
| **Купа** | 512 Б (`_Min_Heap_Size = 0x200`) | `STM32F411xx_FLASH.ld` | Купа FreeRTOS (`configTOTAL_HEAP_SIZE`) для TCB, стеків, черг |
| **Статична оцінка стека** | найбільші кадри: `w25_self_test` 528 Б, `Console_Handle` 360 Б; найгірший ланцюжок (команда `FTEST`) ≈ 1,1–1,3 КБ — більше за резерв 1024 Б | `.su` (`docs/metrics/memory.txt`) | Окремий стек на задачу, розмір — за `uxTaskGetStackHighWaterMark()` |
| **Найбільший буфер у RAM** | `cam_framebuffer` 50 688 Б (39,6 % RAM): більший зі смуги CIF 32 × 1312 = 41 984 Б і знімка QCIF 176 × 144 × 2 = 50 688 Б | `make nm-stats` | Без змін |
| **Flash / RAM загалом** | text 60 552, data 512, bss 54 664 Б → Flash 61 064 Б (11,6 % з 512 КБ), RAM 55 176 Б (42,1 % з 128 КБ, разом з резервом стека й купи) | `arm-none-eabi-size` | Більше на розмір ядра, стеків задач і TCB |

**Не виміряно в ЛР3:** пік стека (`stack_report()` не викликається; для ЛР4 — додати виклик раз на 10 с або командою UART і записати `used_peak`), рядки `FLASH` / `RAM` з `--print-memory-usage` (числа вище — з `arm-none-eabi-size`, `docs/metrics/memory.txt`).

## 3. Відтворення сценаріїв

Збірка `make build`, прошивка `make flash`. Кожен лог починається рядком з хешем збірки:

```bash
echo "# fw $(git rev-parse --short HEAD) $(date '+%F %T') <назва>" > docs/metrics/<назва>.log && picocom -b 115200 --imap lfcrlf /dev/ttyACM0 | tee -a docs/metrics/<назва>.log
```

| Сценарій | Що робити |
| :--- | :--- |
| Номінальний | 30+ с без дій, один жест рукою (сцена освітлена так, щоб `lum` ≥ 70) |
| run_btn | Saleae 2 МГц: CH0 B1/PC13, CH1 PC9, CH2 PC8. 10 циклів: B1 → посередині передачі кадру ще раз B1 → дочекатися `OK` і 2–3 `TICK`. В одному циклі під час передачі — 20 команд `PING` з другого терміналу |
| run_i2c_recovery | 15 с норми → від'єднати SDA біля MPU6050 на 10 с → повернути → 30 с |
| run_reset | Reset; у лозі мають бути `SELFTEST`, 10 записів журналу, `READY` |
| run_long_1h | 1 год без дій |
| Відмова (S3, S4) | від'єднати SDA/SCL (обрив) або замкнути SDA на GND (КЗ) після 10 с роботи і повернути через 10 с |

Зведення: `python3 scripts/lab3_stats.py docs/metrics/run_*.log | tee docs/metrics/summary.txt`.

## Висновок

Super loop стабільно працює в штатному режимі (джитер 12 мс, без втрат UART) і переживає збої шини I2C без зависання. Його принципова межа — одна довга блокувальна операція зупиняє весь продукт: передача кадру тримає систему ≈31 с, а реакція на кнопку залежить від того, на якій задачі перебуває цикл: від мікросекунд до 61 мс у звичайній роботі і до 19,5 с під час передачі.

FreeRTOS у ЛР4 потребуватиме **більше пам'яті** (окремі стеки, TCB, купа ядра). Це прийнятна ціна за **передбачуваний час реакції і періодичність**. Однак дві проблеми FreeRTOS сама не розв'яже: відставання часу через вимкнені переривання під час читання камери (потрібне DMA) і відсутність відновлення шини I2C (потрібна окрема логіка).
